# Продуктовое проектирование

## 1. Проблема и ценностные предложения

**Проблема:** турникеты по картам создают очереди и трение при проходе, теряются/ломаются карты, случаи «забыл карту» требуют ручной обработки охраной.

**Ценностные предложения:**

- **Для сотрудника:** проход без карты, без задержки на доставание/прикладывание карты. Потенциал сокращения времени в очереди. Не нужно искать карту в сумке/кармане.
- **Для охраны:** меньше рутинных запросов «забыл карту», освобождается время на реальные инциденты безопасности. Текущие 40 случаев/день × 4 мин = 160 мин/день ручной работы.
- **Для бизнеса:** возврат продуктивного времени сотрудников, снижение операционных расходов (перевыпуск карт: 300 шт/год × 250 ₽), сокращение нагрузки на охрану.

## 3. Топ-2 гипотезы

### Гипотеза 1: Быстрый проход по лицу с достижимой FRR

**Целевая когорта:** все 12 000 сотрудников на 3 входах (19 000 проходов/день)

**Ожидаемый эффект метрик:**
- p95 времени service прохода: 6 с → ≤ 1 с (экономия 5 с на транзакцию)
- FRR ≤ 3% должна быть валидирована в теневом режиме
- Статистический FAR будет измерен; критерий безопасности пилота: 0 подтверждённых false accept

**Метод валидации:** теневой режим на 1 входе (2 камеры). Система распознаёт лица, но не управляет турникетом. Сравнение решений системы с фактом прохода по карте.

**Параметры валидации:**
- Длительность: определяется объёмом выборки для измерения FRR по подгруппам (освещение, демография, время суток, погода)
- Минимальный объём: достаточный для статистически значимой оценки FRR по релевантным условиям съёмки

**Критерий фальсификации:**
- FRR > 10% overall (слишком много отказов легитимным сотрудникам)
- FRR сильно различается по подгруппам (систематический bias)
- Latency p95 > 1 с
- **Любой подтверждённый false accept в пилоте → немедленная остановка автоматического доступа, откат к assisted/card**

**Условие отката:** подтверждённый false accept, рост реальных инцидентов безопасности, p95 latency деградирует, FRR не достигает порога.

### Гипотеза 2: Фолбэк на повтор/карту вместо ручной проверки охраной

**Целевая когорта:** случаи технической неопределённости (плохое освещение, blur, low confidence модели, occlusion). Доля таких случаев будет измерена в теневом режиме.

**Ожидаемый эффект метрик:**
- Снижение нагрузки на охрану зависит от доли технических отказов vs security ambiguity
- Ручная проверка резервируется для случаев security ambiguity (неизвестное лицо, несколько кандидатов, подозрительное поведение), НЕ для технического качества кадра
- Среднее время разрешения технического случая: 4 мин → 10–15 с (повтор или карта)

**Метод валидации:** анализ логов теневого режима с классификацией причин отказа (техническая vs security). Затем assisted-режим: система подсказывает «повторите» или «используйте карту» при техническом отказе.

**Параметры валидации:**
- Длительность определяется объёмом данных для классификации причин отказа
- Измерить: compliance с подсказками «повторите»/«карта»

**Критерий фальсификации:**
- Доля технических отказов недостаточна для значимого снижения нагрузки на охрану
- Пользователи не следуют подсказкам (измерить compliance)

**Условие отката:** рост жалоб сотрудников, охрана перегружена, автоматический фолбэк снижает security compliance.

**Операционное ограничение:** при 20 проходах/мин/вход и 5% manual review rate появляется 1 новый случай/мин, а один review = 4 мин. Без параллельных reviewers или быстрого технического фолбэка очередь будет расти неограниченно. Это обосновывает жёсткий guardrail на долю случаев, идущих на ручную проверку.

## 4. Продуктовые метрики

### North Star

**Доля проходов сотрудников, автоматически завершённых без подтверждённого false accept при ML decision latency ≤ 1 с.**

Измеряет одновременно успешность распознавания (adoption), скорость ML решения и безопасность. Падение метрики сигнализирует проблему в любом из трёх измерений.

**Примечание:** ML decision latency (≤1 с) — это техническое требование времени от кадра до команды турникету. Общее время прохода (от подхода до открытия) зависит от поведения сотрудника и будет измерено в пилоте.

### Guardrails

1. **Подтверждённые false accepts:**
   - Критерий пилота: **0 подтверждённых false accept**
   - Статистический FAR измеряется отдельно, но любой подтверждённый инцидент в пилоте останавливает автоматический доступ
   - При нарушении: немедленная остановка автоматических пропусков, откат в assisted-режим, forensic review всех проходов за последние 24 ч

2. **False Reject Rate (FRR) легитимных сотрудников:** отказы без успешного автоматического прохода / все попытки прохода
   - Целевой порог пилота: ≤ 3%
   - Кандидат на production target: ≤ 1% (требует валидации достижимости)
   - Измерение: overall и по релевантным подгруппам (освещение, углы, демография)
   - При нарушении: фриз раскатки, анализ причин (освещение, углы камер, демография), улучшение модели или инфраструктуры перед продолжением

3. **Доля проходов, идущих на ручную проверку охраной:**
   - Порог пилота: ≤ 1%
   - При 20 проходах/мин/вход: 1% = 0.2 случая/мин
   - При ~4 мин/случай: требует ~0.8 reviewer-минут/мин/вход в среднем
   - Это высокая утилизация; должны также наблюдаться длина очереди и доступность reviewer
   - При нарушении: усиление retry/card фолбэка; если очередь на review растёт — откат в assisted mode

### Baseline и целевые значения

| Метрика | Baseline (карты) | Цель пилота (лицо) | Measurement |
|---------|------------------|---------------------|-------------|
| North Star: доля проходов с FAR=0, ML latency ≤1 с | ~0% | ≥ 90% | Edge timestamps + security logs |
| ML decision latency p95 | N/A | ≤ 1 с | Edge device: frame → turnstile command |
| Общее время прохода p95 | 6 с | Измерить в пилоте | Video analytics: approach → open |
| Подтверждённые false accepts | Неизвестна (карты крадут/теряют) | 0 в пилоте | Security incident reports + video review |
| FRR (overall) | ~0% (карта всегда работает, если есть) | ≤ 3% pilot | False reject events / total attempts |
| Доля manual review | ~0.2% (40/19000) | ≤ 1% pilot | Manual review queue logs |

## 5. Экономика

### Исходные данные (given, supplied by task)

- 12 000 сотрудников, 19 000 проходов/день
- 45% проходов в пиковые часы (8 550/день в пик)
- 3 входа × 2 камеры = 6 камер
- Пиковая нагрузка: 20 проходов/мин/вход
- Текущий p95 прохода по карте: 6 с
- Целевой ML decision latency: ≤ 1 с (техническое требование)
- Текущее пиковое ожидание в очереди: 90 с/чел (observed)
- Ручная проверка охраной: 40 случаев/день × 4 мин/случай × 120 ₽/случай
- Перевыпуск карт: 300 шт/год × 250 ₽ = 75 000 ₽/год
- CAPEX: 3 × 150 000 ₽ (GPU) + 6 × 30 000 ₽ (камеры) = 630 000 ₽
- Рабочих дней: 250/год
- **Стоимость времени сотрудника: 10 ₽/мин** (given)

### Явные предположения (explicit assumptions)

- **Общее время прохода по лицу:** зависит от поведения подхода, не равно ML decision latency
  - Downside: 5 с (экономия 1 с)
  - Base: 4 с (экономия 2 с)
  - Upside: 3 с (экономия 3 с)
- Обслуживание инфраструктуры: **5 000 ₽/месяц** (assumption)
- Операции (обновление моделей, мониторинг, инциденты): **10 000 ₽/месяц** (assumption)
- **Annual OPEX: 180 000 ₽/год** (assumption)
- FRR pilot: 3% (validation target, must be measured)
- FRR retry delay: 10 с (assumption)
- Снижение перевыпуска карт: зависит от adoption, не моделируется в базовом сценарии (малый вклад)
- Снижение нагрузки на охрану: зависит от доли технических vs security отказов, не моделируется в базовом сценарии до измерения

### Сценарии экономического эффекта

**ВАЖНО:** ML decision latency ≤1 с — это техническое требование, НЕ общее время прохода. Общее время прохода (от подхода до открытия) зависит от поведения сотрудника и должно быть измерено в пилоте.

**Базовый сценарий (4 с общее время прохода, без очередей):**

- Прямая экономия времени: (6 с - 4 с) × 19 000 проходов/день × 250 дней = 9 500 000 с/год = 2 639 чел×час/год
- Ценность: 2 639 ч × 600 ₽/ч = **1 583 333 ₽/год**
- FRR loss (3%): 19 000 × 0.03 × 10 с × 250 дней = 1 425 000 с/год = 396 чел×час/год = 237 500 ₽/год
- **Годовой net (базовый): 1 583 333 - 237 500 - 180 000 (OPEX) = 1 165 833 ₽/год**
- **Payback (базовый): 630 000 / 1 165 833 = 0.540 года ≈ 197 дней**

**Downside сценарий (5 с общее время прохода, без очередей):**

- Экономия: (6 с - 5 с) = 1 с
- Годовой net: 791 667 - 237 500 - 180 000 = **374 167 ₽/год**
- Payback: **630 000 / 374 167 ≈ 1.68 года ≈ 615 дней**

**Upside сценарий (3 с общее время прохода, без очередей):**

- Экономия: (6 с - 3 с) = 3 с
- Годовой net: 2 375 000 - 237 500 - 180 000 = **1 957 500 ₽/год**
- Payback: **630 000 / 1 957 500 ≈ 0.322 года ≈ 117 дней**

**Чувствительность к очереди (базовый + queue reduction, НЕ включено в базовый case):**

- Если пиковая очередь снижается на 30 с: дополнительная экономия **10 687 500 ₽/год**
- Базовый net + queue: 1 165 833 + 10 687 500 = **11 853 333 ₽/год**, payback ≈ 19 дней

**Дополнительные возможные выгоды (не включены в базовый case, требуют валидации Гипотезы 2):**

- Снижение нагрузки на охрану: зависит от измеренной доли технических vs security отказов
- Если технические отказы составляют 75% от 40 случаев/день: экономия ~30 случаев/день × 4 мин × 120 ₽ = 3 600 ₽/день × 250 = **900 000 ₽/год**
- Снижение перевыпуска карт (малый вклад): при 50% снижения = **37 500 ₽/год**

### Чувствительность к FRR (базовый сценарий: 4 с общее время прохода)

| FRR | FRR Loss (₽/год) | Net Benefit (₽/год) | Payback (дней) |
|-----|------------------|---------------------|----------------|
| 1%  | 79 167           | 1 324 167           | 174            |
| 3%  | 237 500          | 1 165 833           | 197            |
| 5%  | 395 833          | 1 007 500           | 228            |
| 10% | 791 667          | 611 667             | 376            |

FRR до 5% умеренно влияет на экономику. При FRR 10% payback превышает 1 год.

### Стоимость security incident (planning scenario assumption)

Подтверждённый false accept = серьёзный инцидент безопасности. Для целей планирования принимаем минимальную оценку ущерба **500 000 ₽** (расследование, аудит, репутация). Реальный ущерб при проникновении злоумышленника может быть на порядки выше и зависит от последствий. Эта цифра НЕ является оценкой фактического/юридического ущерба, а служит для обоснования критичности FAR = 0 в пилоте.

## 6. Раскатка (rollout)

### Фазы

1. **Теневой режим (shadow mode):** 1 вход
   - Система распознаёт, но не управляет турникетом
   - Проход по картам как обычно
   - Логируются решения системы, latency, качество изображений
   - Цель: измерить FRR (overall и по подгруппам), latency, классифицировать причины отказа (техническая vs security)
   - Длительность: определяется объёмом выборки для статистически значимого измерения FRR по релевантным условиям

2. **Assisted-режим:** 1 вход
   - Система открывает турникет при high confidence
   - Low confidence или технический отказ → подсказка «повторите» или «карта»
   - Security ambiguity → эскалация охране (как сейчас)
   - Цель: валидация фолбэков, UX, compliance с подсказками, сбор corner cases
   - Длительность: определяется объёмом данных для измерения compliance и UX

3. **Полный автоматический режим на 1 входе (пилот):**
   - Автоматическое открытие при распознавании
   - Фолбэк на карту доступен
   - Ежедневный мониторинг всех guardrails
   - **Stop condition: любой подтверждённый false accept**
   - Длительность: достаточная для валидации стабильности метрик

4. **Раскатка на все 3 входа:** поэтапно
   - После успешного пилота на 1 входе
   - Мониторинг всех guardrails
   - Быстрый откат при нарушении порогов

### Контрольные точки (milestones)

| Milestone | Критерий успеха | Решение при провале |
|-----------|-----------------|---------------------|
| M1: Shadow mode завершён | FRR ≤ 10% overall, нет систематического bias по подгруппам, latency p95 ≤ 1 с, 0 false accepts в логах | FRR > 10% → улучшение модели/камер; bias → улучшение training data; latency > 1 с → оптимизация inference |
| M2: Assisted mode завершён | Compliance с подсказками измерен, доля технических отказов классифицирована, нагрузка на охрану измерена | Low compliance → пересмотр UX; недостаточная доля технических отказов → пересмотр Гипотезы 2 |
| M3: Пилот на 1 входе | 0 подтверждённых false accepts, FRR ≤ 3%, ML latency p95 ≤ 1 с, доля manual review ≤ 1%, North Star ≥ 90% | Любой false accept → стоп, forensic review, архитектурный пересмотр; другие метрики → доработка |
| M4: Раскатка на 3 входа | Стабильные метрики на всех входах | Деградация метрик → откат проблемных входов, доработка |

### Команда и роли

- **CV/ML:** модель распознавания, embeddings, re-identification, continuous improvement по corner cases
- **Backend:** система принятия решений (confidence thresholds, fallback logic), интеграция с HR API (employee DB), логирование и аналитика
- **Edge/Infrastructure:** edge inference на GPU, camera management, latency optimization, мониторинг hardware
- **Security:** threat modeling, forensic review процедуры, аудит логов, интеграция с физической безопасностью
- **Operations:** обучение охраны, процедуры эскалации, мониторинг дашборды, incident response playbooks

## 7. Стоп-критерии

**Немедленная остановка (полный откат к картам или assisted-режиму):**
- Любой подтверждённый false accept во время пилота или production
- Рост реальных инцидентов безопасности, связанных с системой
- Очередь на manual review растёт неограниченно (reviewer capacity исчерпана)

**Фриз раскатки (остановка распространения на новые входы, сохранение текущих):**
- FRR > 3% на пилоте стабильно
- ML decision latency p95 > 1 с стабильно > 48 ч
- Доля manual review > 1% (высокая утилизация reviewer capacity)
- Рост жалоб сотрудников на проход

**Пересмотр архитектуры:**
- Невозможность достичь целевой FRR при 0 подтверждённых false accepts после итераций улучшения
- Edge GPU capacity недостаточна для пиковой нагрузки (latency растёт с нагрузкой)
- Систематический bias по демографическим группам не устраняется
- Невозможность удержать manual review ≤ 1% при приемлемой FRR

## 8. Явные предположения, гипотезы и неизвестные

**Предположения в экономике:**
1. Общее время прохода по лицу (от подхода до открытия): downside 5 с, base 4 с, upside 3 с (assumption scenarios, будет измерено в пилоте)
2. OPEX 180 000 ₽/год покрывает обслуживание, обновления моделей, мониторинг (assumption)
3. FRR retry delay 10 с (assumption, будет измерено в assisted mode)
4. Стоимость false accept incident ≥ 500 000 ₽ (planning scenario assumption для обоснования критичности FAR=0, НЕ оценка фактического/юридического ущерба)

**Гипотезы, требующие валидации:**
1. FRR ≤ 3% достижима на разнообразной демографии при качественных камерах и освещении
2. Технические отказы (blur, occlusion, освещение) составляют значимую долю всех отказов (измерить в shadow mode)
3. Сотрудники будут следовать подсказкам «повторите» / «карта» (измерить compliance в assisted mode)
4. Быстрый проход снижает пиковую очередь (измерить effect в пилоте)
5. Снижение нагрузки на охрану достижимо через технический фолбэк (Гипотеза 2)

**Неизвестные (требуют измерения):**
1. Реальное распределение FRR по демографическим группам, времени суток, погоде, освещению
2. Доля технических vs security отказов
3. Compliance с подсказками «повторите»/«карта»
