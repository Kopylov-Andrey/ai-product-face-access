# Мониторинг

## 1. Назначение

Мониторинг демонстрирует:
1. Работоспособность инфраструктуры (задержка, доступность)
2. Доставку продуктовой ценности (решена ли исходная проблема?)
3. Соблюдение безопасности (без неприемлемых затрат на безопасность)

Мониторинг проверяет работу продуктовых гипотез, а не только операционную панель.

## 2. Технические Метрики

**Задержка:**
- ML-решение p50/p95/p99 (целевая p95 ≤1 с)
- Разбивка: обнаружение, PAD, embedding, ANN, политики, решение, команда
- Отдельно по проходной и камере
- **Оповещение:** устойчивое превышение p95 >1 с вызывает техническое оповещение и расследование. Окно устойчивости для подавления ложных срабатываний настраивается по данным теневого режима.

**Доступность:**
- Камера, узел edge, связность турникета, время работы
- Успешность команд, соотношение ACK/NACK

**Согласованность Версий и Снимков:**
- Отставание версий политик, шаблонов, индекса по каждому edge
- Подтверждённая метка отзывов
- **Распространение отзывов — наивысший приоритет.** Порог отставания калибруется в теневом режиме и пилоте. Состояние устаревших или неизвестных политик → автоматический биометрический допуск запрещён.

**Очередь Аудита в Автономном Режиме:**
- Размер очереди, возраст, сбои синхронизации
- Оповещение: неограниченный рост → исследовать

**Производительность ANN:**
- **Задержка ANN должна вписываться в сквозной бюджет ≤1 с.**
- **Полнота ANN-поиска измеряется в автономном режиме относительно точного поиска** и выбирается с учётом требований к задержке.

## 3. ML Метрики

### Продуктовый Уровень FAR/FRR

**FAR (False Accept Rate):** неавторизованные проходы. Измерение: подтверждённые инциденты безопасности, служебное расследование.

**FRR (False Reject Rate):** отказы легитимным. Измерение: биометрические отказы, требующие повтора, карты или ручной проверки; жалобы; проход по карте после биометрического отказа.

**Границы (из product.md):**
- **Любой подтверждённый false accept** → остановить автоматический режим
- **FRR >3% в пилоте** → заморозить раскатку, исследовать

### Системный Уровень 1:N Identification Метрики

**FPIR, FNIR** — правильные метрики для оценки 1:N identification.

**Rank-1/Rank-K accuracy:** правильная личность в лучших результатах.

**Почему обе:** FAR/FRR понятны заинтересованным сторонам. FPIR/FNIR корректны для технической оценки 1:N. Отслеживать обе.

### Ручная Проверка

- **Общая доля, разбивка по причинам** (пограничное совпадение, низкая уверенность, спуфинг, устаревшие политики, техническая)
- **Длина очереди, время ожидания**
- **Граница:** >1% или растущая очередь → усиление резервных вариантов, откат в ассистирующий режим

### Quality/PAD/Технические

- **Сбои качества:** размытие, освещение, окклюзия → `DENY/CLOSED` с `next_action` на повторный кадр или карту. Разбивка по камерам.
- **Сбои PAD:** доля подозрений на спуфинг, доля неопределённых. Отдельно по типу атаки если образцы доступны.
- **Пороговый базовый уровень:** установлен в теневом режиме и пилоте, не изобретён.

### Дрейф Входных Данных

Распределения освещения, позы, окклюзии, качества со временем. Значительный сдвиг → проверить модель на новых данных, рекалибровать пороги.

### Разбивка По Условиям

**Критично:** агрегированные метрики могут скрывать сильную деградацию на отдельной камере или проходной. Требуется FRR, задержка, качество отдельно по проходной, камере, времени суток.

## 4. Бизнес-Метрики

**Ссылка на product.md:**

**North Star:** доля проходов, автоматически завершённых без подтверждённого FA при задержке ML-решения ≤1 с. Целевой показатель для пилота: ≥90%.

**Время прохода:** общее время p95, базовый уровень 6 с, измерить в пилоте.

**Доля автоматических проходов:** биометрический ALLOW против повтора, карты, ручной проверки.

**Нагрузка на охрану:** случаи ручной проверки в день, очередь, использование пропускной способности. Цель: снижение рутинных случаев.

## 5. Оповещения

**Продуктовые границы (используются как оповещения):**
- Любой подтверждённый FA → остановить автоматический режим
- FRR >3% в пилоте → исследовать или откат
- Ручная проверка >1% или растущая очередь → резервные варианты или ассистирующий режим
- Задержка ML устойчиво >1 с → техническое оповещение

**Другие сигналы:** порог установлен на базовом уровне теневого режима и пилота (доступность камеры, скачок отказов качества, сбои PAD, отставание версии).

## 6. Изоляция Причин

**Деградация одной камеры:** скачок FRR изолирован → проблема камеры или освещения.

**Деградация одной проходной:** затронуты все камеры → проблема edge или окружения.

**Все проходные после обновления модели:** корреляция с временной меткой версии → регрессия модели.

**Все проходные после обновления индекса или политик:** корреляция с передачей данных → проблема управляющего контура.

## 7. Расследование Аудита

**Корреляция событий по event_id:**

проходная/камера → версии модели/индекса/политики → оценки качества/PAD/совпадения → решение и причины → результат команды → результат ручной проверки → отложенные метки (жалобы, проход по карте, инцидент безопасности).

**Обратная связь отложенных меток:** проверка порогов, обнаружение систематического смещения, улучшение модели, выяснение причины инцидента.

## 8. Проверка Продуктовых Гипотез

**Гипотеза 1** (быстрый проход, FRR ≤3%): отслеживать снижение времени прохода, фактическую FRR, 0 подтверждённых FA.

**Гипотеза 2** (технический резервный вариант): отслеживать снижение ручной проверки, следование повторам и карте, нагрузку на охрану.

**Критерии успеха:** North Star ≥90%, 0 подтверждённых FA, FRR ≤3% в пилоте, ручная проверка ≤1%, улучшенное время прохода относительно базового уровня.

Мониторинг проверяет продуктовые предположения, а не только работоспособность инфраструктуры.
