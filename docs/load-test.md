# Нагрузочный smoke-test

Скрипт `scripts/load_smoke.py` проверяет конкурентную обработку событий в
реализованном PoC: детерминированный decision engine, симуляцию команды турникету
и формирование локального JSONL-аудита.

## Что проверяется

В условии задан пик до 20 проходов/мин на одну проходную. Для трёх проходных это
расчётно до 60 событий/мин, то есть около 1 события/с по кампусу. Поэтому smoke-test
имеет три профиля:

| Профиль | Предлагаемая нагрузка | Назначение |
|---|---:|---|
| `baseline` | 1 событие/с | расчётный общий пик трёх проходных |
| `burst` | 3 события/с | кратковременный запас относительно входных данных |
| `stress` | 5 событий/с | стрессовый smoke-профиль PoC |

Профили циклически включают `happy`, `risky`, `spoof`, `offline`, `revoked` и
`low_quality`, чтобы вместе с производительностью проверять fail-safe поведение.

## Запуск

Все три профиля:

```bash
python -m scripts.load_smoke
```

Один профиль:

```bash
python -m scripts.load_smoke --profile stress
```

Машиночитаемый результат:

```bash
python -m scripts.load_smoke --profile stress --json
```

Вывод содержит число запросов и ошибок, фактический throughput, p50/p95/p99
локальной обработки, распределение решений, число audit-записей и
`unsafe_open_count`.

## Критерий безопасности

Для нагрузочного smoke-test обязательны:

- `errors = 0`;
- `audit_records = requests`;
- `unsafe_open_count = 0`.

То есть увеличение конкуренции не должно превращать `spoof`, неоднозначную
идентификацию, отозванный доступ или устаревшую политику в `OPEN`.


## Контрольный 60-секундный прогон

Локально выполнен профиль `stress` с предлагаемой нагрузкой 5 событий/с:

| Метрика | Результат |
|---|---:|
| Запросы | 300 |
| Ошибки | 0 |
| Фактический throughput | 5.02 событий/с |
| p50 | 0.725 мс |
| p95 | 0.879 мс |
| p99 | 1.056 мс |
| Audit records | 300 |
| `unsafe_open_count` | 0 |

Эти числа относятся к конкретному локальному запуску mock decision/audit-контура и **не являются production-бенчмарком CV/ML**.

## Ограничение результата

Это **не production-бенчмарк CV/ML**. В PoC detection, quality, PAD/liveness,
embedding и ANN представлены детерминированными синтетическими сигналами.
Полученные p95/p99 измеряют только накладные расходы реализованного
`decision + turnstile simulation + local audit` контура на конкретной машине.

Целевой end-to-end p95 ≤ 1 с для настоящего CV/ML pipeline должен отдельно
подтверждаться на выбранных моделях, ANN-индексе и целевом edge GPU.
